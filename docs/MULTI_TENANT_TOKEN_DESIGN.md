# Design Proposal: Tenant-Scoped Bearer Tokens

> **Status:** DRAFT for architecture and security review.
> This change touches authentication. It must receive a human security review (WI-008) before implementation.

## 1. Problem

Today the plugin authenticates every SCIM call against a single static secret, `grails.scim.api_token`, compared in `ScimControllerInterceptor`. Tenant information only appears inside the payload (the `tenants` / `tenant` custom extension) and is supplied by the caller. Consequences:

- One shared secret per deployment. Every identity provider (IdP) configured against the same host application uses the same token, so a leaked token exposes all tenants.
- No server-side tenant binding. A caller can write any tenant id into the extension block; the plugin cannot verify the caller is allowed to touch that tenant.
- Per-client onboarding currently needs a dedicated deployment or a dedicated token, which does not scale across many clients.

## 2. Goal

Allow one SCIM base URL (`/scim/v2`) on one host application to serve many tenants. Each client's IdP receives its own bearer token that identifies its tenant, so:

- The plugin derives the tenant from the token, never from the URL or payload.
- Each tenant has its own secret. A leaked token or a leaked server-side secret exposes one tenant only.
- Tenants can be onboarded, rotated and revoked without redeploying and without a central token-issuing service.
- Existing single-token installations keep working unchanged.

## 3. Non-goals

- Replacing the bearer scheme with OAuth 2.0 client credentials or introducing a token verifier service. This design keeps the `Authorization: Bearer <token>` contract that IdPs such as Okta, Entra ID and SailPoint already support, and needs no issuer.
- Hiding the tenant id from the token holder. The tenant id is treated as an identifier, not a secret. Section 9 describes how to add that later if required.
- Storing tenant or token records inside the plugin. Persistence stays in the host application, consistent with the existing `ScimResourceRepository` delegation model.

## 4. Token format (recommended)

The token is a two-part credential. No cryptography beyond a constant-time comparison is needed in the plugin, and no new dependencies are required.

```
<base64url(tenantId)>.<base64url(tenantSecret)>
```

| Part | Description |
|---|---|
| `tenantId` | Identifier of the tenant the token belongs to. Validated against `^[A-Za-z0-9._-]{1,64}$` after decoding. |
| `tenantSecret` | A random secret generated by the host administrator for that tenant, at least 32 bytes from `SecureRandom`. |

Base64url encoding keeps the token header-safe and lets tenant ids contain characters that would otherwise conflict with the `.` separator. It is encoding, not encryption; the tenant id is readable by anyone holding the token, which is acceptable under the non-goals above.

A legacy static secret can never be mistaken for a tenant token: the parser requires exactly two non-empty base64url parts, and the interceptor checks the static token first.

### 4.1 Verification flow

1. Split the bearer value on the first `.`. Reject if there are not exactly two non-empty parts, if either part fails base64url decoding, or if the whole value exceeds 1 KB.
2. Decode the first part to obtain `tenantId` and validate it against the pattern above before using it anywhere, including log statements.
3. Resolve the expected secret for that tenant through `ScimTenantKeyResolver` (section 4.2).
4. Compare the presented secret with the expected value using `MessageDigest.isEqual` on byte arrays. The resolver returns the SHA-256 hash of the secret, and the interceptor hashes the presented secret before comparing, so plaintext secrets never need to be held server-side.
5. On success set `ScimTenantContext.tenantId = tenantId`. On any failure return the existing SCIM 401 body without revealing whether the tenant exists.

### 4.2 Key resolution

```groovy
package grails.plugins.scim.security

interface ScimTenantKeyResolver {
    /**
     * Returns the SHA-256 hash (hex or base64) of the tenant's secret,
     * or null when the tenant is unknown or disabled.
     */
    String resolveSecretHash(String tenantId)
}
```

The plugin ships `ConfigScimTenantKeyResolver`, a default bean that reads a tenant-prefixed config key. The tenant id is the top-level prefix so that each tenant's settings sit together and can be supplied by a tenant-specific config source:

```
<tenantId>.grails.scim.api_token
```

```yaml
tenant-001:
  grails:
    scim:
      api_token: ${SCIM_TOKEN_HASH_TENANT_001}   # sha256 of the secret
tenant-002:
  grails:
    scim:
      api_token: ${SCIM_TOKEN_HASH_TENANT_002}
```

The resolver builds the key as `"${tenantId}.grails.scim.api_token"` only after the tenant id has passed the pattern check in section 4.1, so untrusted input can never reach the config lookup unvalidated. It reads the value with `grailsApplication.config.getProperty(key, String)` and returns null when absent.

Hosts that onboard tenants at runtime override the bean with a database, cache or vault lookup. Implementations should cache lookups briefly, must never log the returned value, and must return null rather than throw for unknown tenants so the failure path stays uniform.

### 4.3 Onboarding a tenant

1. Administrator generates a 32-byte random secret and base64url-encodes it.
2. Administrator stores `sha256(secret)` under `<tenantId>.grails.scim.api_token` in config, or in the host's tenant table if a custom resolver is used.
3. Administrator hands the client IdP the token `base64url(tenantId).base64url(secret)`. The plaintext secret is shown once and not retained.
4. Rotation: store the new hash, give the client the new token, remove the old hash. Revocation: remove the hash or disable the tenant so the resolver returns null.

A small helper `ScimTenantTokenParser.build(tenantId, secret)` is provided for the host's admin tooling so the format is produced in one place.

## 5. Request flow after the change

```
IdP ──Authorization: Bearer <b64(tenantId)>.<b64(secret)>──▶ ScimControllerInterceptor
                                                               │ 1. grails.scim.enabled?                 → 403 if false
                                                               │ 2. legacy static token match?           → authenticated, no tenant context
                                                               │ 3. ScimTenantTokenParser.parse()        → tenantId + presented secret
                                                               │ 4. ScimTenantKeyResolver.resolveSecretHash(tenantId)
                                                               │ 5. MessageDigest.isEqual(sha256(presented), expected) → 401 on mismatch
                                                               │ 6. ScimTenantContext.set(tenantId)
                                                               ▼
                                                    ScimUserController / ScimGroupController
                                                               │ if context set: payload tenant(s) ignored, overwritten from context
                                                               ▼
                                                    ScimUserService / ScimGroupService
                                                               ▼
                                                    host ScimResourceRepository (reads ScimTenantContext when set)
                                                               │
                                                    interceptor after() → ScimTenantContext.clear()
```

## 6. Proposed changes

### 6.1 New classes in `src/main/groovy/grails/plugins/scim/security/`

| Class | Responsibility |
|---|---|
| `ScimTenantTokenParser` | Pure parsing and building of the two-part token. Owns the part-count, length, base64url and tenant-id pattern checks. Throws `InvalidScimTokenException` on any failure without indicating which check failed. `@CompileStatic`. |
| `ScimTenantKeyResolver` | Interface in section 4.2. |
| `ConfigScimTenantKeyResolver` | Default implementation backed by `<tenantId>.grails.scim.api_token` config keys. Registered in `doWithSpring()` only when no host bean of that type exists. |
| `ScimTenantContext` | Request-scoped holder for `tenantId`. Backed by a request attribute plus a `ThreadLocal` for code that has no request handle. Cleared in the interceptor's `after()` and on exception. Exposes `static String currentTenantId()` returning null when unset. |
| `InvalidScimTokenException` | Thrown by the parser. Mapped to the existing SCIM 401 error body. |

### 6.2 `ScimControllerInterceptor`

- Replace the direct string comparison with a two-step strategy: first the legacy static token check, then tenant-token verification.
- Move the legacy comparison to `MessageDigest.isEqual` on byte arrays.
- On tenant-token success populate `ScimTenantContext`. On any failure return the existing SCIM-formatted 401. Log the tenant id and client IP at trace level on success; on failure log only the IP and a reason code, never the header value.
- Add `after()` and exception handling to clear the context so thread reuse in Tomcat cannot leak a tenant between requests.
- Keep the legacy path behind `grails.scim.legacyStaticToken.enabled` (default `true` for one release, then `false`).

#### Legacy static-token flow in detail

The legacy flow is payload-driven. It does not use `ScimTenantContext` at all.

1. If `legacyStaticToken.enabled` is true, compare the bearer value with `grails.scim.api_token` using `MessageDigest.isEqual`.
2. On a match the request is authenticated. **No `ScimTenantContext` is set.** Host repositories behave exactly as they do today and read tenant information from the resource objects they receive.
3. If there is no match, fall through to tenant-token verification. If that also fails, return the existing SCIM 401.
4. The `tenants` (User) and `tenant` (Group) custom extension fields remain supported and remain the only tenant source for legacy requests.
5. **No tenant validation and no injection.** The controller performs no tenant check on legacy requests. Whatever tenant information the payload carries is passed to the repository unchanged, and if the extension block is absent the resource simply has no tenant data. Nothing is defaulted in. This is exactly today's behaviour.
6. Tenant interpretation for legacy requests therefore stays entirely with the host repository, as it does now.

The two flows are mutually exclusive per request and are summarised below.

| | Legacy static token | Tenant token |
|---|---|---|
| Authentication | Constant-time match on `grails.scim.api_token` | Constant-time match of `sha256(secret)` against the tenant's stored hash |
| `ScimTenantContext` | Not set | Set with `tenantId` |
| Tenant source | Payload extension fields | Token |
| Payload tenant fields | Honoured as sent | Ignored and overwritten with the context tenant |
| Repository behaviour | Unchanged from today | Scope all reads and writes to context tenant |

### 6.3 Controllers

- In `fromJson` and in `patch`, after binding, branch on whether `ScimTenantContext` is set.
  - **Context set (tenant-token flow)**: the tenant is taken from the context and is mandatory. Any `tenants` / `tenant` values in the payload are ignored, not rejected. The controller overwrites the custom extension so that `ScimUser.customExtension.tenants == [contextTenant]` and `ScimGroup.customExtension.tenant == contextTenant`. For PATCH, operations whose `path` targets the extension tenant attribute are dropped before the request reaches the repository. If the context is somehow absent on this path the interceptor has already rejected the request, so controllers never see a tenant-token request without a tenant.
  - **Context not set (legacy flow)**: the payload is accepted as-is with no tenant handling.
- Ignoring rather than rejecting payload tenants keeps IdPs that send a static extension block working without configuration changes, while guaranteeing the repository only ever sees the authenticated tenant.
- For `index` and `show`, the tenant filter is applied by the host repository via the context, so no controller change is required beyond the above.

### 6.4 Repository contract

`ScimResourceRepository` keeps its signature to avoid breaking existing host implementations. Implementations call `ScimTenantContext.currentTenantId()`. When it returns a value the repository must scope every read and write to that tenant and must throw `ResourceNotFoundException` for ids that belong to a different tenant, never leak their existence. When it returns null the request came through the legacy path and the repository behaves as it does today.

A future major version can add a `tenantId` parameter to the interface explicitly.

### 6.5 Configuration

| Key | Default | Purpose |
|---|---|---|
| `<tenantId>.grails.scim.api_token` | none | SHA-256 hash of that tenant's secret, one key per tenant. Used by the default resolver. |
| `grails.scim.legacyStaticToken.enabled` | `true` | Allows `grails.scim.api_token` as a fallback. Set `false` to force tenant tokens only. |

Startup validation in `GrailsScimGrailsPlugin.doWithSpring()`: because tenant keys are prefixed by tenant id, the plugin cannot enumerate them cheaply at startup. Validation is therefore done lazily on first lookup per tenant: a configured value that is not a valid 32-byte digest after decoding is logged once as a configuration error and treated as absent. If `legacyStaticToken.enabled` is false and the host has not configured any tenant or custom resolver, every request is rejected with 401, which is the safe failure mode.

### 6.6 Discovery endpoints

`ScimHomeController.buildServiceProviderConfig` keeps `type: bearertoken`. The `/docs/scim-auth` page gains a short paragraph stating that tokens are tenant-scoped and provided by the host administrator. No change to the SCIM schema documents.

### 6.7 No issuance endpoint

The plugin deliberately adds no HTTP endpoint for creating tokens or tenants. Onboarding (section 4.3) runs through the host application's own administrator tooling, which already sits behind its own authentication. The plugin contributes only the parser helper and the resolver interface.

## 7. Security considerations

- **Secret handling**: the server stores only `sha256(secret)`. A database or config leak does not yield usable tokens. Secrets are at least 256 bits of entropy, so hashing without salt is sufficient; there is nothing to brute-force.
- **Timing attacks**: both the legacy comparison and the hash comparison use `MessageDigest.isEqual`.
- **Enumeration**: unknown tenant, wrong secret and malformed token all return the same 401 body and take the same code path, so tenant ids cannot be probed.
- **Token in logs**: the existing interceptor logs the full `Authorization` header on failure. That line must change to log only the IP and reason code.
- **Tenant isolation**: enforced in two places. The controller overwrites any payload tenant with the authenticated tenant, so payload tampering cannot move a resource to another tenant. The repository scopes reads and writes by the context, so ids cannot be probed across tenants. Both are needed.
- **Replay and expiry**: tokens are long-lived bearer credentials by design, as SCIM IdPs require. There is no built-in expiry; rotation is an operational task via the resolver. Transport must be TLS only.
- **Input validation**: the parser rejects tokens over 1 KB, with wrong part counts, invalid base64url, or tenant ids outside the allowed pattern, before any lookup.
- **Blast radius**: a leaked token exposes one tenant. A leaked server-side hash exposes nothing directly. There is no master key whose loss would expose every tenant.

## 8. Backward compatibility and rollout

1. Release N: ship the new classes with `legacyStaticToken.enabled=true`. Existing deployments see no behaviour change. Hosts that want multi-tenancy add `<tenantId>.grails.scim.api_token` entries or provide a resolver bean and hand tokens to clients.
2. Hosts migrate IdP integrations client by client. Both token styles work during migration.
3. Release N+1: default `legacyStaticToken.enabled` to `false`. Deprecate `grails.scim.api_token` in the changelog.
4. Release N+2 (next major): remove the legacy path and add `tenantId` to `ScimResourceRepository`.

## 9. Future option: hiding the tenant id

If a client later requires that the tenant id not be visible to the token holder, the first part of the token can be replaced by an AES-256-GCM ciphertext of the tenant id under a single plugin-wide key, with a `kid` prefix for rotation. Only `ScimTenantTokenParser` changes; the resolver, context, controller and repository contracts stay the same. This is deliberately deferred because it reintroduces a master key whose compromise affects all tenants, and because tenant ids are not currently considered sensitive.

## 10. Testing plan

Unit specs under `src/test/groovy/grails/plugins/scim/security/`, following the existing `ControllerUnitTest` / `InterceptorUnitTest` conventions:

- `ScimTenantTokenParserSpec`: build and parse round trip; one part, three parts, empty parts, invalid base64url, oversized input and tenant ids outside the pattern each throw; `build` output is accepted by `parse`.
- `ConfigScimTenantKeyResolverSpec`: returns the hash from `<tenantId>.grails.scim.api_token`, returns null for unknown tenants, treats a malformed hash as absent, never builds a key from an unvalidated tenant id.
- `ScimControllerInterceptorSpec`: extend the existing spec with tenant-token success, wrong secret, unknown tenant, legacy fallback on and off, context populated and cleared for tenant tokens, context absent for legacy tokens, and 401 body shape unchanged across all failure cases.
- `ScimUserControllerSpec` / `ScimGroupControllerSpec`: tenant-token flow, payload tenants are replaced by the context tenant, absent extension is populated from the context, and PATCH operations targeting the tenant attribute are dropped; legacy flow, payload tenants pass through untouched and a missing extension is accepted.

## 12. Addendum (M4): per-tenant signed JWT

Some clients hold a per-tenant HMAC secret and want to present a standard signed JWT instead of the two-part tenant token. M4 adds this as a third, mutually exclusive flow with the same downstream behaviour.

### 12.1 Token shape

```
base64url({"alg":"HS256","typ":"JWT","kid":"<keyId>","tid":"<tenantId>"})
.base64url({"iss":"<idp>","sub":"scim","iat":...,"exp":...,"jti":"..."})
.base64url(HMAC-SHA256(header + "." + payload, tenantSecret))
```

`tid` and `kid` sit in the header so the secret can be located before verification. The header is part of the signed input, so neither value can be altered without invalidating the signature; they are read before verification and trusted only after it.

### 12.2 Verification

1. Detection: exactly three non-empty dot-separated parts routes to the JWT flow; two parts routes to the tenant token flow. Legacy static token is still checked first.
2. `ScimJwtParser.readHeader`: `alg` must be exactly `HS256`; `tid` and `kid` must match the id pattern. `none` and asymmetric algorithms are rejected before any lookup.
3. `ScimTenantJwtSecretResolver.resolveSecret(tid, kid)`; null rejects.
4. Recompute HMAC-SHA256 over the first two parts and compare with `MessageDigest.isEqual`. The payload is not decoded before this step.
5. Claims: `exp` mandatory and not past `now + skew`; `nbf` if present not after `now + skew`; payload `tid` if present must equal header `tid`; `iss` must equal `expectedIssuer(tid)` when that returns non-null.
6. `ScimTenantContext.set(tid)`. Controllers and repositories behave exactly as in the tenant token flow.

### 12.3 Key resolution and configuration

| Key | Purpose |
|---|---|
| `<tenantId>.grails.scim.jwt.<kid>` | Base64 raw HMAC secret, at least 32 bytes. Several `kid` entries per tenant allow rotation. `issuer` is reserved and cannot be a kid. |
| `<tenantId>.grails.scim.jwt.issuer` | Optional. When set, `iss` must match. |
| `grails.scim.jwt.clockSkewSeconds` | Default 60. |

Default bean `scimTenantJwtSecretResolver` is `ConfigScimTenantJwtSecretResolver`; hosts override it by bean name. A short or malformed secret is logged once and treated as absent.

### 12.4 Security notes

- The secret must be stored raw because HMAC needs the key bytes. This differs from the tenant token, which stores only a hash. Secrets must come from environment or vault, never committed config.
- Algorithm is pinned server-side; the header `alg` is checked for equality, never used to select an algorithm.
- `exp` is mandatory, which is the main benefit of JWT over the unexpiring tenant token.
- No new dependencies: `javax.crypto.Mac`, `java.util.Base64` and `JsonSlurper` only.

## 11. Decisions

The following questions were raised during review and resolved on 2026-10-16.

| Question | Decision |
|---|---|
| Should `ConfigScimTenantKeyResolver` accept plaintext secrets as well as hashes? | **Hashes only.** A configured value that does not decode to a 32-byte SHA-256 digest is treated as absent and logged once as a configuration error. Plaintext secrets are never read from config. |
| Do client IdPs impose a bearer token length or character limit that affects the format? | **No.** No such limit is known for the IdPs in scope. The 1 KB parser limit stands as a defensive bound only. |
| Does the first release need a UI for tenant secret management? | **No.** Config-file management via `<tenantId>.grails.scim.api_token` is acceptable initially. A runtime store and admin UI can be added later by overriding `ScimTenantKeyResolver`, with no plugin change. |
